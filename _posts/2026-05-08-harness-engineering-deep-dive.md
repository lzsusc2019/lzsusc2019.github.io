> **快速回想**：
> - **概念**：Harness Engineering（牵引工程）是指围绕 AI 代理构建物理沙箱、权限约束以及自动化测试反馈循环，从而保障大模型输出可靠性的工程实践。
> - **纵向演进**：从单纯依赖提示词（Prompt Engineering）走向提供参考资料库（RAG），再到如今通过执行环境控制模型行为（Harness Engineering）。
> - **核心差异**：Prompt 试图提升单次输出正确率；RAG 补充私有上下文；Harness 接受模型会犯错的前提，通过工程手段（如重试、拦截、静态检查）进行兜底。
{: .prompt-info }

在探讨 AI Agent 落地生产环境的过程中，Harness Engineering（牵引工程）逐渐取代了早期的各种 Prompt 技巧，成为架构设计中的核心关注点。

与那些试图通过特定前缀词或逻辑链条来让模型“变聪明”的做法不同，Harness Engineering 回归了传统的软件工程视角：它预设了大模型在执行复杂任务时必定会产生不确定性（熵增），从而将精力集中在外围防御和反馈机制的建设上。

## 一、纵向分析：控制手段的演进逻辑

### 1. 早期阶段：依赖指令的局限性
在 2022 到 2023 年大模型刚开始普及时，开发者的主要控制手段是 Prompt Engineering。试图通过不断微调指令格式、添加 few-shot 示例或要求模型输出推导过程来获取稳定的代码。
这种方式的约束条件很明显：模型的输出质量高度依赖于底层基座版本。同一个优秀的 Prompt，在模型版本切换后往往会产生截然不同的效果，缺乏工程上的可复现性。

### 2. 权限扩大带来的真实风险
到了 2024 年初，随着各种 Agent 框架的普及，AI 开始拥有了真实的执行权限——它们可以读写文件、运行 Shell 命令甚至提交代码。
当模型在开放环境中执行任务时，幻觉带来的后果被放大了。例如，在修复一个简单的编译错误时，模型可能会在没有明确指令的情况下，擅自重构不相关的模块，或者执行破坏性的环境清理命令。这种不可控性使得单纯的文本约束不再奏效。

### 3. Harness Engineering 作为工程防护网的诞生
面对上述问题，开发者开始引入传统的隔离与测试机制。Harness Engineering 应运而生，它的发展经历了几个可见的阶段：
- **物理隔离**：最早期的形态是将 Agent 放入 Docker 容器中执行，确保其行为不会影响宿主机环境。
- **权限最小化**：剥夺 Agent 的全局读写权限，仅对必要目录开放接口。
- **自动验证与闭环**：这是 Harness 走向成熟的关键节点。系统在 Agent 产出代码后，自动拉起项目的 Linter、类型检查和单元测试。如果失败，Harness 会将真实的控制台报错信息截获，重新反馈给 Agent 促使其自我修正。在这个循环中，人类工程师不直接参与，Harness 承担了质量守门员的角色。

## 二、横向分析：当前控制 AI 的三种路径

在当前的 AI 研发流中，为了确保模型输出的可用性，业界形成了三种互补的路径。

### 1. Prompt Engineering
- **定位**：对输入端进行格式化控制。
- **实践表现**：它依然是与大模型交互的基础。但在复杂项目中，开发者逐渐发现，过长的 Prompt 反而会分散模型的注意力（Lost in the middle）。目前它的作用更多地退回到定义任务边界和初始角色的基本层面，不再被视为解决复杂逻辑的银弹。

### 2. RAG（检索增强生成）
- **定位**：解决信息不对称问题。
- **实践表现**：当模型面临需要了解特定业务架构或私有 API 时，RAG 发挥着关键作用。它在输入阶段为模型挂载了准确的事实基准。但 RAG 只能保证模型获取的信息是对的，无法保证模型基于这些信息执行的代码逻辑是完整的。

### 3. Harness Engineering
- **定位**：对输出端及执行过程进行工程约束。
- **实践表现**：它将传统软件工程的基础设施（CI/CD、自动化测试、静态分析）前置到了 AI 生成环节。真实的开发体验是，无论前置的 Prompt 写得多么简陋，只要 Harness 提供的验证条件足够严苛，系统就能通过机器之间的多轮迭代，最终逼出一段能通过所有测试的代码。
- **缺点**：引入 Harness 的成本较高。开发者需要为不同的编程语言和框架构建适配的沙箱环境，并编写解析各种报错日志的基础设施。

## 三、横纵交汇：传统工程实践的回归

将大模型的演进脉络与当下的几种控制流派结合来看，AI Agent 架构的演化实际上是软件工程常识的一次回归。

随着各个主流基础大模型能力的趋同，通过更换模型或微调指令来获取代码质量提升的红利正在见顶。未来，决定一个 Agent 系统是否能在企业内部落地的关键，将从单纯的“模型推理能力”，转移到外围 Harness 的健壮性上。

当系统能够提供足够安全、隔离的执行环境，并在每次修改后提供极其精确的代码检查和运行日志反馈时，即便是普通智商的开源模型，也能通过穷举式的迭代完成任务。

这其实传递了一个务实的信号：管理 AI 与管理人类程序员在思路上是同构的。与其花费大量精力去祈祷它们一次性写出完美的系统，不如花时间去完善你的测试用例、CI 流程和运行沙箱。约束体系的质量，最终决定了 AI 产出的下限。
